# WSync — техплан

Утилита синхронизации сейвов Minecraft между двумя ПК через Яндекс.Диск.
Windows + macOS, Electron + TypeScript + React.

---

## 1. Термины

В коде и UI **нет** «импорта/экспорта» — они читаются двусмысленно. Только:

| Операция | Направление | Что делает |
|---|---|---|
| **Upload** («Выгрузить в облако») | ПК → облако | архивирует локальный мир, кладёт в облако, старую облачную копию убирает в облачные бэкапы |
| **Download** («Загрузить на ПК») | облако → ПК | скачивает архив, локальный мир убирает в локальные бэкапы, распаковывает новый |

---

## 2. Ключевые инварианты

Их нельзя нарушать ни в одной ветке кода:

1. **Ничего не удаляется до успеха.** Старый сейв уходит в бэкап через `rename`, а не удаляется. Реальное удаление — только ротацией бэкапов, отдельным проходом.
2. **Замена — через два `rename` в пределах одного тома.** Нет момента, когда старого сейва уже нет, а нового ещё нет.
3. **Целостность проверяется до подмены.** Скачали → сверили размер и sha256 с манифестом → только потом трогаем `saves/`.
4. **Операция при запущенной игре запрещена.** Проверка блокировки `session.lock`.
5. **Любая ошибка оставляет систему в валидном состоянии.** Есть шаг откат/cleanup для каждой фазы.

## 3. Структура на Яндекс.Диске

Приложение работает в собственной папке (`app:/`, scope `cloud_api:disk.app_folder`) — доступа к остальному диску у него нет.

```
app:/                              → Яндекс.Диск/Приложения/WSync/
  atm10/
    manifest.json                  индекс всех миров сборки
    lock.json                      кто взял мир и когда (advisory, не жёсткий лок)
    saves/
      MyWorld/part0001 part0002 …  части архива, передаются параллельно
    backups/
      MyWorld__2026-08-05_19-22-10/part0001 …
```

### manifest.json

```jsonc
{
  "version": 1,
  "instanceId": "atm10",
  "worlds": {
    "MyWorld": {
      "archive": "saves/MyWorld.zip",
      "archiveSize": 4821993472,
      "sha256": "e3b0c442...",
      "uncompressedSize": 5310000000,
      "entryCount": 28714,
      "lastPlayed": 1754650000000,   // из level.dat, мс
      "uploadedAt": 1754651234567,
      "uploadedBy": "HOME-PC",
      "appVersion": "0.1.0"
    }
  }
}
```

`lastPlayed` из `level.dat` — единственный надёжный признак «какая версия мира новее». Время файла врёт (копирование, синк, распаковка сбрасывают mtime).

### lock.json

```jsonc
{ "world": "MyWorld", "machine": "HOME-PC", "takenAt": 1754651234567, "operation": "download" }
```

Не блокирует принудительно — показывает предупреждение. Жёсткий лок в утилите на два ПК только мешает (забыл снять — заблокировал себя).

## 4. Разрешение конфликтов

Единый список миров: локальные и облачные в одной таблице. Статус считается сравнением `lastPlayed` локального `level.dat` и `lastPlayed` из манифеста:

| Статус | Условие | Что предлагаем |
|---|---|---|
| `synced` | `lastPlayed` совпадают | ничего |
| `local-only` | нет в манифесте | Upload |
| `cloud-only` | нет локально | Download |
| `local-newer` | локальный `lastPlayed` больше | Upload (безопасно) |
| `cloud-newer` | облачный больше | Download (безопасно) |
| `diverged` | оба менялись после общей точки | **⚠ подтверждение с явным текстом** что и чем будет перезаписано |

`diverged` определяется так: при каждой операции в локальные метаданные мира пишется `syncedLastPlayed` — значение на момент последней успешной синхронизации. Если и локальный, и облачный `lastPlayed` больше `syncedLastPlayed` — играли с двух сторон, расхождение.

Это тот самый случай, который иначе съедает прогресс молча.

## 5. Архивация

- Формат: zip.
- **`.mca`, `.mcc` — `store` (level 0).** Внутри region-файлов чанки уже сжаты zlib; повторный deflate даёт единицы процентов и упирает архивацию в CPU. Со `store` процесс ограничен диском.
- Остальное (`level.dat`, `.json`, `serverconfig/`, `.dat`) — deflate level 6.
- `session.lock` в архив не попадает.
- sha256 считается стримом одновременно с записью архива — второго прохода по 8 ГБ нет.
- Прогресс — по количеству обработанных байт от предварительно посчитанного суммарного размера.

## 6. Облачный слой

Интерфейс `CloudProvider` — чтобы Google Drive позже добавлялся как второй бэкенд без правок ядра:

```ts
interface CloudProvider {
  ensureFolder(path: string): Promise<void>
  list(path: string): Promise<CloudEntry[]>
  stat(path: string): Promise<CloudEntry | null>
  readJson<T>(path: string): Promise<T | null>
  writeJson(path: string, data: unknown): Promise<void>
  upload(localPath: string, remotePath: string, opts): Promise<CloudEntry>
  download(remotePath: string, localPath: string, opts): Promise<void>
  move(from: string, to: string): Promise<void>
  remove(path: string): Promise<void>
  quota(): Promise<{ total: number; used: number }>
}
```

### Яндекс.Диск REST

| Что | Запрос |
|---|---|
| инфо о диске / квота | `GET /v1/disk/` |
| листинг | `GET /v1/disk/resources?path=app:/...&limit=...` |
| создать папку | `PUT /v1/disk/resources?path=app:/...` |
| выгрузить | `GET /v1/disk/resources/upload?path=...&overwrite=true` → `PUT` на выданный `href` |
| скачать | `GET /v1/disk/resources/download?path=...` → `GET` по `href` |
| переместить | `POST /v1/disk/resources/move?from=...&path=...` (может вернуть 202 + операцию) |
| удалить | `DELETE /v1/disk/resources?path=...&permanently=true` |

Метаданные ресурса содержат `md5`/`sha256` — после выгрузки сверяем с локально посчитанным хешем. Это подтверждение целостности от сервера, а не только «запрос вернул 201».

HTTP — на `node:https` напрямую, а не fetch: нужен точный прогресс по байтам, свои таймауты, retry с экспоненциальной задержкой и докачка через `Range` при обрыве скачивания.

### OAuth

Authorization Code + **PKCE (S256)**, без client_secret в бинарнике.

Единственный поток — ручной ввод кода через `https://oauth.yandex.ru/verification_code`. Локальный редирект на `127.0.0.1` реализовать не удалось: зарегистрировать `http://localhost:...` как Redirect URI у приложения Яндекса не выходит, а держать ветку, которая гарантированно не работает, вреднее, чем одно копирование кода.

`client_id` пользователь регистрирует сам на oauth.yandex.ru и вводит в настройках — зашить его в открытый код нельзя. Инструкция в README.

**Права передаются явно и настраиваются.** Яндекс, вопреки документации, не подставляет права приложения при отсутствии параметра `scope`: пустой scope даёт ту же ошибку `invalid_scope`, что и запрос лишнего права. Поэтому scope — поле в настройках, по умолчанию `cloud_api:disk.app_folder cloud_api:disk.info`. Права запоминаются вместе с токеном: если настройки разошлись с выданным токеном, UI предупреждает, что нужно переподключиться.

**Сведения о диске необязательны.** `GET /v1/disk/` требует `cloud_api:disk.info`; без него Диск отвечает 403. Проверка свободного места — удобство, а не условие: её провал только пишет предупреждение в журнал и не отменяет выгрузку. На том шаге облачная копия ещё не тронута.

Токены (`access_token`, `refresh_token`) — через Electron `safeStorage` (DPAPI на Windows, Keychain на macOS), шифрованными в `userData`. Без нативных модулей вроде keytar.

## 7. Алгоритмы

### Upload (ПК → облако)

```
0. проверить: игра не запущена (session.lock), мир существует, авторизация валидна
1. посчитать размер мира → проверить свободное место в облаке (GET /v1/disk/)
2. прочитать level.dat → lastPlayed
3. прочитать облачный manifest.json → определить статус
   если diverged / cloud-newer → потребовать явного подтверждения в UI
4. записать lock.json { operation: "upload" }
5. заархивировать в <бэкапы>/.wsync_tmp/MyWorld__<ts>.zip, считая sha256 и md5 на лету
6. выгрузить архив в app:/atm10/saves/.tmp_MyWorld.zip
7. сверить sha256 из метаданных ресурса с локально посчитанным
      ↳ несовпадение → удалить .tmp, abort, ничего не тронуто
8. если в облаке есть saves/MyWorld.zip → move в backups/MyWorld__<ts>.zip
9. move .tmp_MyWorld.zip → saves/MyWorld.zip
10. обновить manifest.json (запись мира)
11. ротация облачных бэкапов (оставить N последних)
12. записать локально syncedLastPlayed = lastPlayed
13. снять lock.json, удалить temp-архив
```

### Download (облако → ПК)

```
0. проверить: игра не запущена, авторизация валидна
1. прочитать manifest.json → размер архива, sha256, lastPlayed
2. определить статус локальной копии
   если diverged / local-newer → потребовать явного подтверждения
3. проверить свободное место на диске: archiveSize + uncompressedSize + запас
4. записать lock.json { operation: "download" }
5. скачать в <бэкапы>/.wsync_tmp/MyWorld__<ts>.zip (retry + Range-докачка при обрыве)
6. сверить размер и sha256 с манифестом
      ↳ несовпадение → удалить temp, abort, локальный сейв не тронут
7. распаковать в <saves>/.wsync_tmp_MyWorld/
8. проверить наличие level.dat в распакованном → иначе abort
9. если <saves>/MyWorld существует → rename в <backups>/MyWorld__<ts>
10. rename .wsync_tmp_MyWorld → MyWorld
11. записать локально syncedLastPlayed
12. ротация локальных бэкапов
13. снять lock.json, удалить temp
```

Обе операции — конечный автомат с явными фазами; каждая фаза знает свой cleanup. Отмена пользователем идёт через `AbortSignal` и выполняет тот же cleanup.

### Ротация бэкапов

- Настройка: «хранить N последних бэкапов на мир» (по умолчанию 3) и «не больше X ГБ».
- Удаление — **только** после успешного завершения всей операции. Никогда в середине.
- В UI кнопка «Открыть папку бэкапов».

## 13. Отклонения от плана по ходу реализации

Решения, принятые уже в коде, — здесь, чтобы план не расходился с репозиторием.

**`archiver` 7.x, не 8.x.** Восьмая версия — чистый ESM без вызываемого экспорта по умолчанию, а main собирается в CJS: `require()` на неё падает. Седьмая — CJS, тот же API, зрелая.

**Временные файлы — в `<каталог бэкапов>/.wsync_tmp`, а не в системном temp.** По умолчанию каталог бэкапов лежит рядом с `saves`, то есть на том же томе. Это даёт мгновенные `rename` вместо копирования между дисками и требует свободного места только на одном томе. Если пользователь развёл каталоги по разным дискам, UI об этом предупреждает.

**Сверка по md5 как запасной вариант.** Яндекс отдаёт в метаданных ресурса и `sha256`, и `md5`, но не гарантирует появление обоих сразу после приёма файла. `createZip` считает оба хеша одним проходом, и сверка идёт по тому, который сообщил Диск. Если не сообщил ни одного — проверяется только размер, и в журнал пишется предупреждение.

**Пустые каталоги сохраняются.** `datapacks/`, `advancements/` и подобные попадают в архив явными записями: Minecraft их пересоздаст, но возвращать мир байт-в-байт правильнее.

**`client_secret` — опциональное поле в настройках.** PKCE закрывает авторизацию, но Яндекс требует секрет при обновлении токена. Без него всё работает, только по истечении токена нужно подключиться заново.

**Свой минимальный читатель NBT** (`core/nbt.ts`, ~150 строк) вместо `prismarine-nbt`: из `level.dat` нужны два поля, а библиотека тянет `protodef` со всем его графом зависимостей.

**В интерфейсе нет пояснительных текстов.** Справка живёт в README; позже вернётся в UI подсказками под значком «?». В UI остались только подписи полей, статусы и сообщения об ошибках.

**Архив хранится частями и передаётся параллельно.** Это оказалось единственным, что реально влияет на скорость. Измерено на живом канале: один поток — 126 КБ/с, четыре — 474 КБ/с, ×3.8. При 237 Мбит/с уплинка это значит, что упор не в полосу, а в одиночное соединение до дальнего ДЦ. Части — байтовые диапазоны готового zip, второй копии на диске не появляется; при загрузке они пишутся параллельно по своим смещениям в заранее созданный файл, поэтому промежуточных файлов тоже нет. Целостность проверяется по каждой части, отдельный проход по всему архиву не нужен.

Что при этом **не** помогло, хотя выглядело правдоподобно: смена размера читаемых с диска кусков и перевод выгрузки на сетевой стек Chromium вместо `node:https` (тайминги совпали с точностью до двух секунд). Chromium-транспорт оставлен как основной с автоматическим откатом на Node, но выигрыша по скорости он не дал.

**Прогресс передачи честен только до момента отдачи данных.** Сколько байт подтвердил получатель, пользовательскому процессу узнать нельзя ни в одном стеке. Поэтому проценты считаются по байтам, отданным операционной системе, а после отдачи всего тела UI переходит в ожидание без процентов и ETA — вместо «осталось 1 с», за которым следовали три минуты тишины.

**Смоук-тест** (`tools/smoke-test.ts`, `npm run smoke`) собирает синтетический мир и проверяет чтение NBT, round-trip архивации, совпадение хешей, ротацию бэкапов, все восемь статусов, защиту от zip-slip и чистоту отмены — 19 проверок без сети и без облака.
