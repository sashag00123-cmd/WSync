# WSync

Синхронизация миров Minecraft между двумя компьютерами через Яндекс.Диск.
Windows и macOS, Electron + TypeScript + React.

Технические решения и обоснования — в [PLAN.md](PLAN.md).

В интерфейсе пояснительных текстов нет — вся справка живёт здесь. Позже она вернётся в UI в виде подсказок под значком «?».

---

## Что делает

Одна таблица со всеми мирами: и локальными, и облачными, со статусом каждого.

- **Выгрузить в облако** — мир упаковывается в zip, кладётся в облако, прежняя облачная копия уходит в облачные бэкапы.
- **Загрузить на ПК** — архив скачивается, сверяется по sha256, локальный мир уходит в бэкапы, распакованный встаёт на его место.

Гарантии, которые не нарушаются:

1. Ничего не удаляется до успеха — старая копия **переносится** в бэкапы, а не затирается.
2. Подмена локального мира — два `rename`: момента «старого уже нет, нового ещё нет» не существует.
3. Целостность проверяется до подмены: размер + sha256 (или md5, если Диск не отдал sha256).
4. Операция при запущенной игре блокируется (проверка `session.lock`).
5. Расхождение («играли и здесь, и там») показывается отдельным статусом и требует явного подтверждения.

## Установка для разработки

```bash
npm install
```

Если бинарник Electron не скачался автоматически:

```bash
node node_modules/electron/install.js
```

Запуск в режиме разработки:

```bash
npm run dev
```

Проверки:

```bash
npm run typecheck
```

```bash
npm run smoke
```

`smoke` собирает синтетический мир (включая region-файлы, пустой каталог и кириллицу в `level.dat`) и проверяет чтение NBT, round-trip архивации, совпадение хешей, ротацию бэкапов, все статусы синхронизации, защиту от zip-slip и корректность отмены.

## Сборка приложения

Иконка генерируется из знака приложения средствами Chromium (отдельный конвертер SVG не нужен). Пересобирать её надо только если меняли рисунок в `tools/make-icon.cjs`:

```bash
npm run icon
```

### Windows

```bash
npm run dist:win
```

Результат — `release/WSync-0.1.0-win-x64.exe`, установщик NSIS примерно на 97 МБ. Ставится **для текущего пользователя, без прав администратора**, каталог установки можно выбрать.

Вариант без установщика — папка, которую достаточно скопировать:

```bash
npm run dist:win:portable
```

Даёт `release/win-unpacked/` с `WSync.exe` внутри. Запакуйте в zip и носите на флешке — установка не требуется, настройки всё равно лягут в профиль пользователя.

### macOS

**На Windows это собрать нельзя** — для `.dmg` нужен сам macOS. Два пути:

1. **На Mac.** Скопируйте проект без `node_modules`, затем:

```bash
npm install && npm run dist:mac
```

Получатся `release/WSync-0.1.0-mac-arm64.dmg` (Apple Silicon) и `-x64.dmg` (Intel).

2. **Через GitHub Actions** — см. следующий раздел.

### Сборка через GitHub Actions

Workflow лежит в `.github/workflows/build.yml` и собирает обе платформы: Windows на `windows-latest`, macOS на `macos-latest`. Перед сборкой прогоняются `typecheck` и `smoke`.

Запуск вручную — **Actions → build → Run workflow**; готовые файлы лежат в артефактах задания (90 дней, нужен вход в GitHub).

Запуск по тегу дополнительно создаёт релиз с установщиками, которые доступны по прямой ссылке:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

Публикация из electron-builder отключена флагом `--publish never`. Без него сборщик определяет CI и сам пытается выложить релиз, падая на отсутствии `GH_TOKEN`; релиз собирается отдельным заданием через `gh`, которому хватает встроенного `GITHUB_TOKEN`.

### Ключи приложения в сборке

Чтобы установщик приходил уже настроенным и `client_id` не приходилось вставлять на каждой машине, ключи вшиваются на этапе сборки из переменных окружения:

| Переменная | Секрет репозитория |
|---|---|
| `WSYNC_YANDEX_CLIENT_ID` | `YANDEX_CLIENT_ID` |
| `WSYNC_YANDEX_CLIENT_SECRET` | `YANDEX_CLIENT_SECRET` |
| `WSYNC_YANDEX_SCOPE` | `YANDEX_SCOPE` (необязательно) |

Секреты добавляются в **Settings → Secrets and variables → Actions**. Локально то же самое делается переменными окружения:

```bash
$env:WSYNC_YANDEX_CLIENT_ID = '...'; $env:WSYNC_YANDEX_CLIENT_SECRET = '...'; npm run dist:win
```

Если переменных нет, значения остаются пустыми и приложение просит ключи в настройках. Вшитое значение используется только когда в сохранённом конфиге поле пустое, так что настройки пользователя оно не перетирает.

В сборке с вшитыми ключами поля для их ввода **свёрнуты** в блок «Ключи приложения — вшиты в сборку»: обычному пользователю в них делать нечего. Совсем убирать их нельзя — они нужны при запуске из исходников без переменных окружения, при диагностике прав и если вшитый ключ придётся перевыпустить.

**Граница честности:** секрет, попавший в распространяемое приложение, секретом быть перестаёт — его можно извлечь из бандла. Секреты репозитория защищают ключи в исходниках и логах CI, но не в готовом бинарнике. Для личного приложения на два компьютера это приемлемо, тем более что авторизация построена на PKCE, а `client_secret` нужен только для обновления токена. Если ключи утекут — перевыпустите секрет в кабинете Яндекса кнопкой ↻.

### Версии

Номер версии берётся из `version` в `package.json` и попадает в имя файла. Автообновления нет: новая версия — это новый установщик.

## Передача на другой компьютер

### Windows

Скопируйте `WSync-0.1.0-win-x64.exe` любым способом — флешка, облако, сеть — и запустите.

При первом запуске Windows покажет **SmartScreen: «Не удалось проверить издателя»**. Это нормально для приложения без сертификата подписи кода: нажмите «Подробнее» → «Выполнить в любом случае». Убрать предупреждение можно только купив сертификат (от 200 $ в год) и подписав им сборку.

### macOS

Скопируйте `.dmg`, откройте, перетащите WSync в «Программы».

Приложение не подписано, поэтому Gatekeeper заблокирует первый запуск. Обходится так: **правый клик по WSync → «Открыть»** → в диалоге ещё раз «Открыть». Начиная с macOS Sequoia может потребоваться **Системные настройки → Конфиденциальность и безопасность → «Открыть всё равно»**.

Альтернатива в терминале:

```bash
xattr -dr com.apple.quarantine /Applications/WSync.app
```

Чтобы предупреждения не было, нужны подпись и нотаризация: Apple Developer Program (99 $ в год), переменные `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` и удалённая строка `identity: null` из `electron-builder.yml`.

### Настройка второй машины

Что должно **совпадать** с первой машиной:

- `client_id` и, если задан, `client_secret` — то же приложение Яндекс.OAuth;
- запрашиваемые права;
- **папка в облаке** у сборки — именно по ней машины видят одни и те же миры.

Что должно **различаться**:

- **имя машины** — им подписываются облачные копии, по нему видно, откуда пришёл сейв;
- каталоги `saves` и бэкапов — они свои на каждом компьютере.

Настройки и токены лежат в профиле пользователя (`%APPDATA%\WSync` на Windows, `~/Library/Application Support/WSync` на macOS). **Копировать `tokens.dat` между машинами бессмысленно** — он зашифрован средствами ОС под конкретного пользователя. На второй машине просто пройдите авторизацию заново.

## Первая настройка

### 1. Своё приложение в Яндекс.OAuth

`client_id` нельзя зашить в открытый код, поэтому приложение регистрируется один раз на ваш аккаунт.

1. Откройте <https://oauth.yandex.ru/client/new>.
2. Платформа — **Веб-сервисы**.
3. Redirect URI: `https://oauth.yandex.ru/verification_code` (кнопка «Подставить URL для отладки» вставляет его сама).
4. Права доступа:
   - `cloud_api:disk.app_folder` — доступ к папке приложения на Диске;
   - `cloud_api:disk.info` — сведения о свободном месте.
5. Скопируйте `client_id` в настройки WSync.

Авторизация только с ручным вводом кода: нажимаете «Подключить Яндекс.Диск» → в браузере разрешаете доступ → Яндекс показывает код → вставляете его в поле в настройках и нажимаете «Готово». Локальный редирект на `localhost` не поддерживается — зарегистрировать такой Redirect URI у приложения Яндекса не выходит, поэтому нерабочая ветка убрана.

Приложение получает доступ **только** к своей папке `Яндекс.Диск/Приложения/WSync` — к остальному диску у него доступа нет.

**Права должны совпадать с полем «Запрашиваемые права» в настройках WSync** (по умолчанию `cloud_api:disk.app_folder cloud_api:disk.info`). Яндекс проверяет их строго: запросили право, которого у приложения нет, — вход отвергается целиком с `invalid_scope`; не запросили ничего — та же ошибка, потому что Яндекс считает, что прав не запрошено.

| Право | Что даёт | Без него |
|---|---|---|
| `cloud_api:disk.app_folder` | чтение и запись в папке приложения | ничего не работает, право обязательное |
| `cloud_api:disk.info` | свободное место на Диске | место не показывается, и перед выгрузкой не проверяется, хватит ли его — если не хватит, Диск откажет уже в процессе, ничего при этом не испортив |
| `login:info` | имя аккаунта в шапке | вместо имени просто «Яндекс.Диск» |

Права зашиты в выданный токен: расширили их в кабинете — переподключитесь (Отключить → Подключить), иначе старый токен новых прав не получит. WSync замечает расхождение и предупреждает об этом в настройках.

**`client_secret`** необязателен, но полезен: Яндекс требует его при обновлении токена. Без секрета всё работает, просто по истечении токена WSync попросит подключиться заново.

### 2. Сборка

Настройки → Сборки → **Найти автоматически**. WSync проверит стандартные пути CurseForge, Prism Launcher, MultiMC, Modrinth App, GDLauncher, ATLauncher и ванильного лончера.

Если ничего не нашлось — **Добавить вручную** и выбрать каталог `saves` (тот, внутри которого лежат папки миров с файлом `level.dat`).

Для каждой сборки настраивается:

| Поле | Смысл |
|---|---|
| Каталог saves | откуда берутся и куда ставятся миры |
| Каталог бэкапов | куда переносятся заменяемые миры |
| Папка в облаке | **должна совпадать на обоих компьютерах** — именно по ней машины видят одни и те же миры |

Каталог бэкапов лучше держать на том же диске, что и `saves`: тогда бэкап — мгновенный перенос, а не копирование гигабайтов. Если диски разные, WSync предупредит.

### 3. Второй компьютер

Те же `client_id` (и `client_secret`, если задан), тот же аккаунт Яндекса, **та же папка в облаке**. Имя машины лучше задать разное — оно подписывает облачные копии, по нему видно, откуда пришёл сейв.

## Статусы миров

| Статус | Что значит |
|---|---|
| синхронизирован | локальная и облачная копии совпадают |
| только на ПК / только в облаке | копия есть лишь с одной стороны |
| локальный новее | здесь играли позже — безопасно выгрузить |
| облачный новее | на другой машине играли позже — безопасно загрузить |
| **расхождение** | играли и здесь, и там после последней синхронизации |
| неизвестно | не удалось прочитать `level.dat`, сравнить версии нельзя |

Свежесть определяется по `LastPlayed` из `level.dat`, а не по времени файла: копирование, распаковка и облачные клиенты сбрасывают `mtime`, и он врёт.

**Расхождение** — это тот случай, который обычно и съедает прогресс. WSync его не решает автоматически: он показывает даты последней игры с обеих сторон и требует выбрать. Бэкап при этом создаётся всегда, так что проигравшую версию можно достать.

## Где что лежит

В облаке (`Яндекс.Диск/Приложения/WSync/`):

```
atm10/
  manifest.json          индекс миров: размер, sha256, части, LastPlayed, кто выгрузил
  lock.json              метка «мир взят машиной X» (предупреждающая, не блокирующая)
  saves/MyWorld/part0001 part0002 …
  backups/MyWorld__2026-08-05_19-22-10/part0001 …
```

Мир хранится не одним zip, а частями. Причина измеримая: одно соединение до Яндекса даёт ~126 КБ/с независимо от полосы канала, четыре — ~474 КБ/с. Части передаются параллельно (по умолчанию 8 потоков), размер части подбирается так, чтобы занять все потоки, в границах 4–64 МБ.

Плата за это — **архив нельзя скачать из веб-интерфейса одним файлом**: придётся забрать все части мира и склеить их по порядку имён (`copy /b part0001+part0002+… world.zip` на Windows, `cat part* > world.zip` на macOS). Обычная загрузка через WSync делает это сама.

Локально:

- настройки и токены — каталог `userData` приложения (токены зашифрованы средствами ОС: DPAPI на Windows, Keychain на macOS);
- бэкапы — `<каталог бэкапов>/MyWorld__2026-08-08_14-30-12`;
- временные архивы — `<каталог бэкапов>/.wsync_tmp`, удаляются после операции.

Ротация: хранится N последних бэкапов на мир (по умолчанию 3) плюс общий лимит объёма. Удаление происходит **только** после успешного завершения операции, и последний бэкап мира не удаляется даже при переполнении лимита.

## Известные ограничения

- **Только один мир за раз.** Параллельные операции ломали бы облачный лок.
- **Архив передаётся целиком.** Инкрементальной передачи изменённых region-файлов нет — для двух машин и редкой синхронизации это правильный компромисс, см. PLAN.md.
- **Скорость ограничена Яндексом, а не программой.** Восемь потоков дают примерно ×3.8 к одному, но веб-интерфейс Диска всё равно быстрее: похоже, он использует не публичный REST API. Кнопка «Проверить скорость» в настройках меряет одиночную и параллельную выгрузку на вашем канале.
- **Миры, выгруженные версией до разбиения на части, не читаются.** Они показываются как «только на ПК» и лечатся повторной выгрузкой.
- **Детект «игра запущена» на macOS/Linux** опирается на `lsof`. Если его нет, WSync честно пишет, что проверить не смог, вместо того чтобы молча считать мир свободным.
- **Google Drive не реализован.** Интерфейс `CloudProvider` под него готов, реализации пока нет.
- **macOS без подписи.** Для распространения нужна подпись и нотаризация (Apple Developer Program). Без них приложение запускается, но при первом запуске требует разрешения в System Settings → Privacy & Security.
